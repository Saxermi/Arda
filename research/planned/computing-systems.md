## Draft distributed parameter and gradient ownership contract

**Status** — Design proposal from Vilya 0.17.4. The current runtime implements local autodiff and sample-weighted accumulation. The distributed contract is subject to owner review before implementation.

**Parameter identity and lifetime.** Register each logical parameter with a stable ID, global shape and dtype. Each distributed step refers to one agreed version of every parameter used by its local tapes. Tied weights use one logical ID. The rank's local reverse pass adds all tape contributions for that ID before transport. A buffer address, view or tape slot belongs to one process and cannot identify a distributed parameter. All ranks agree on the parameter list and collective order before computing a step.

**Gradient contributions.** The proposed reduction inputs are a local gradient sum $G_r$ and an exact sample count $n_r$. When the local API has already produced a batch-mean gradient $g_r$, use $G_r=n_r g_r$ once. Batch or microbatch counts add independently of the number of parameter uses. The denominator counts each example in the data partition once, including when multiple parameter shards process it. A rank with an empty batch contributes zero and participates in the same collectives. If a valid batch leaves a registered parameter unused, its contribution for that parameter is zero. Malformed, stale or nonfinite contributions are errors. The global batch mean is $\sum_r G_r / \sum_r n_r$. For two examples with mean derivative 1 and six with mean derivative 3, the result is 2.5. A globally empty batch skips the optimizer step. Sample counts use checked integer arithmetic. Gradient comparisons across reduction orders use a stated tolerance.

**Proposed first implementation.** Each rank holds a replica of the parameters and optimizer state. An ordered collective reduces the sums and counts. Ranks can then stage the same update for the agreed parameter version. Preflight validates rank metadata and local errors before payload collectives, and a completed step publishes only after a coordinated success check. If communication fails or a rank disappears, invalidate that step and recover from an agreed state. Local `ad.backward` retains its existing behavior. When introduced, global clipping would use the reduced gradient before the optimizer, and tied weights would update once per logical parameter. [MPI Forum standard documents](https://www.mpi-forum.org/docs/)

**Alternative to evaluate.** A unique rank owns each parameter shard and its optimizer state. Reduce gradient contributions to the owning shard, apply its update once and publish the new version to readers. Sharding cuts per-rank parameter and optimizer storage, while replicas make local reads and restarts simpler. Sharding adds placement metadata, communication for remote reads, and more complicated failure and restart handling. Keep the logical IDs and weighted-gradient law common to both candidates. Decide ownership granularity and reproducibility requirements before committing to a distributed API.

**Acceptance cases for the later MPI milestone.** Compare unequal and empty batches against a serial concatenated batch. Cover tied parameters with several local contributions, multiple microbatches, repeated or stale step versions, an unused parameter on one rank, matching collective order and errors before any update. Test optimizer-state and parameter-version agreement, restart from one agreed step, and deterministic reduction where enabled. Include actual multi-rank runs before making performance or fault-tolerance claims.
