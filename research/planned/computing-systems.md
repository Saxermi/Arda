# Resource-aware execution and parallel computing

**Status** — Candidates for AME, AKE, ACE, and the 0.23–0.25 interoperability and HPC path. The portable C and optional BLAS/LAPACK CPU builds are the baseline.

| Capability | Baseline and alternatives | Compute, memory and reliability | Recommended experiment |
| --- | --- | --- | --- |
| Buffer ownership, I/O and out-of-core methods | Use checked buffer handles and explicit tiles first. Compare bounded streaming with read-only mmap, LRU caching and prefetch. Compare tiled GEMM, external merge sort, streaming moments and TSQR for tall inputs. | Block scans transfer $O(N/B)$ blocks for $N$ values and block size $B$, with $O(B)$ algorithmic buffer space. Multi-pass work and writeback add traffic. TSQR uses a reduction tree and extra operations on small $R$ factors to limit communication. File cache and RSS differ. | Moderate effort on Linux with local SSD. Verify truncation, invalid headers, alias lifetimes, failure cleanup, deterministic merge order, quotas and rereads under low RAM. Use real data exceeding memory and measure bytes, faults, RSS and throughput for cold and warm runs. |
| ACE planning and compiler integration | Begin with explicit per-operation choices and a measured Roofline-style compute/bandwidth bound. Compare small cached autotuning and later effect-checked graph liveness and tiling. Keep an eager CPU plan. | A planner evaluating $P$ bounded candidates costs at least $O(P)$ planning work. Estimates must include workspace, transfers and fallback. Fusion can reduce intermediate bytes without changing asymptotic work, but reduction reassociation and contraction need explicit policy. | Start with a limited case set and compare measured against estimated time and RSS. Add graph legality, alias and mutation tests plus small-call overhead tests. VM/GC remains single-threaded initially. MLIR is a design reference, with optional toolchain integration subject to review. |
| CPU SIMD and shared-memory parallelism | Compare portable loops with blocked SIMD, thread-pool or optional OpenMP and explicit size cutoffs. Begin with fixed partitions and pairwise or reproducible reductions, then test work stealing, NUMA placement or wider instructions where supported. | Dense GEMM does $O(mkn)$ work and CSR SpMV $O(m+z)$, with distinct arithmetic intensity. Memory bandwidth, synchronization, false sharing and oversubscription can limit speedup well before core count. Reproducible summation adds work and can change the error profile. | Moderate effort for disjoint CPU blocks and higher effort for NUMA tuning. Validate tails, non-contiguous data, determinism, races, backend equivalence and 1/2/4/8-thread scaling. Use accepted dense benchmarks and measure sparse setup and verification separately. |
| GPU and heterogeneous kernels | Choose one optional backend on available hardware. Compare a vendor GEMM against tiled kernels and scalar/warp/row mapping for CSR, using portable CPU references. Later evaluate transfer overlap and residency-aware batching. | SpMV is usually bandwidth-bound and sensitive to row imbalance. Transfers, launch and synchronization overhead can dominate small inputs. FP64 throughput and supported modes differ across devices. Scheduling needs device budgets and safe fallback. | High effort with actual hardware. Measure transfers and setup in end-to-end timings, verify CPU/GPU tolerances, and exercise errors when device features are absent. Use the 2025 portability measurements as a comparator for the platforms and formats studied. |
| MPI and distributed linear operators | Start with row-partitioned CSR, reusable halo plans, nonblocking exchange, global reductions and block Jacobi. Compare partition reorderings, pipelined CG and optional PETSc. Use shard manifests before distributed checkpoint/restart. | Ideal CPU work per balanced rank is about $O((m+z)/p)$, plus halo traffic and at least one synchronization path per iteration. Extra buffering and replicated vectors must be explicit. Pipelining can increase recurrence sensitivity. | High effort. Begin with local ranks and use physical multi-node tests for claims about scaling. Verify count widths, asymmetric faults, global residuals, partition skew, restart and strong/weak scaling. Avoid central full-size gathering. |

**Research evidence** — Use I/O-aware algorithms and communication-avoiding factorizations as baselines. A 2025 task scheduler examines locality under bounded memory. Recent portable SpMV and GPU-accelerated CG studies compare separate architectural regimes. Investigate these after measuring serial Arda kernels at equivalent accuracy.
